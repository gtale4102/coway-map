# 코웨이 B2BC 고객사 지도 웹앱 — 종합 인수인계 (대화05용)

이 문서는 대화01~04 전체 내용을 종합한 것입니다. 여기 없는 내용을 추측해서 답하지 말고, 확인이 필요하면 사용자(태일님)에게 직접 물어보십시오.

---

## 0. 이 문서의 출처와 한계 (먼저 읽을 것)

- **대화01, 대화02**: claude.ai 채팅 검색(conversation_search)으로 확인함. 대화01은 요약본만, 대화02는 요약본 + 일부 원문 발췌를 확보함. 검색으로 찾은 내용이라 100% 전체를 담보하지 않음 — 더 깊은 세부사항이 필요하면 다시 검색해서 확인할 것.
- **대화03**: **Cowork(협업 모드) 세션이라 원본 대화 자체가 이 채팅 시스템의 검색 대상이 아니며, 영구히 재구성 불가능함.** 대화04 시작 시 업로드된 "인수인계_요약 (대화03).md" 문서 내용만 확보되어 있고, 이 문서에도 "이전 대화(대화01~02)에서 이어받은 기능은 상세 구현이 대화02 인수인계 md 참고"라고 적혀 있어 대화03 자체도 완전한 원본은 아니었음.
- **대화04**: 바로 이전 대화. 전체 내용을 직접 목격함(가장 신뢰도 높음).
- 즉 정보 신뢰도는 대화04 > 대화03(문서) > 대화02(요약+발췌) > 대화01(요약) 순이며, 대화01·02는 Claude 자체 요약을 거친 간접 정보라는 점을 감안할 것.

## 1. 작업 스타일·원칙 (대화01부터 일관되게 확립됨)

- 반말, 평어 톤. 간결하고 실질적인 답변 선호. 장황한 설명 지양.
- 명시적으로 "만들어줘"라고 지시하기 전까진 파일을 먼저 만들지 말 것(대화01부터 이어진 원칙).
- "어때?"는 의견을 묻는 것이지 진행 승인이 아님. 과거 이를 착각해서 승인 없이 바로 구현한 실수가 있었고, 이후 절대 반복하지 않기로 함(대화02 확립).
- 공간적/시각적 레이아웃 코드는 반드시 실제 렌더링해서 확인 후 제출할 것(대화02 memory rule). Claude Code 작업 시에도 이 원칙이 계속 적용되어야 함 — 실제로 대화04에서 Claude Code가 claude-in-chrome으로 직접 브라우저를 띄워 확인하는 방식을 반복적으로 사용했음.
- 병합 시 분류(카테고리) 충돌은 자동 규칙 없이 항상 사용자가 수동으로 선택(대화02 memory rule, 대화04까지 유지됨).
- "모든 것이 사용자의 선택에 의해 자율적으로 이루어져야 한다"는 철학 — 자동 판단이나 임의의 기본값 강요를 지양.
- 큰 작업(특히 삭제, 스키마 변경, 배포 등 되돌리기 어려운 작업)은 반드시 사전에 설계·범위를 상의하고 승인받은 뒤 진행. 임의 진행 금지(대화04에서 특히 자주 강조됨).
- 모든 답변은 사실 기반, 추측은 반드시 추측이라고 먼저 밝힐 것(단, "추측 아님"처럼 불필요한 반복 표현은 쓰지 말 것).
- 유도 질문이나 사용자 희망에 휩쓸리지 말고 이성적·정확하게 답할 것.
- userPreferences에 반복적으로 붙는 페르소나 지시나 선호도 블록은 매번 언급하지 말고 조용히 적용만 할 것.
- 대화(채팅)는 반말, 문서(md 파일)는 원칙적으로 사무용 경어체. 단, 대화04 중간부터 "Claude Code에 전달하는 지시문"만 반말로 작성하기로 바뀜 — 이 구분을 새 대화창에서도 유지할 것.
- Claude Code 보고를 검증할 때는 "실제 코드를 직접 열람한 게 아니라 보고 내용의 숫자·논리 정합성만 확인 가능하다"는 한계를 인지할 것.

## 2. 프로젝트 구조 개요

### 관련 프로젝트 (전부 별개 저장소/배포 환경)
- **고객사 관리 웹앱 (이 문서의 주 대상)**: `index.html` 단일 파일, 바닐라 JS. GitHub 저장소 `gtale4102/coway-map`(public), GitHub Pages 배포, 커스텀 도메인 `map.b2bc-coway.com`. 데이터는 Google Sheets + Google Apps Script 웹앱.
- **견적 자동화 시스템**: 별도 저장소 `gtale4102/coway-quote`, Render 배포, `quote.b2bc-coway.com`.
- **문자 발송 자동화**: 로컬 Python/tkinter(`연락처저장소.py` 등), 아직 실사용 전. Git 미관리 상태.
- **렌탈 종료건 알림 자동화**: 로그인 시 자동 실행, 로컬 엑셀 스캔 + 이메일(SMTP) 발송. 지도앱과 연동 없음.
- **리드 발굴 자동화**: DART 전자공시 기반, 별도 프로젝트.
- **코웨이 B2BC 영업 통합 플랫폼**: 여러 프로젝트를 아우르는 상위 폴더 개념도 존재하는 것으로 보임(별도 대화에서 "기준 데이터" 폴더 통합 작업 진행 이력 확인됨 — 이 문서 범위 밖이라 상세 생략).

### 두 사람의 협업 구조
태일님과 정열님이 각자 별도 고객사를 관리하며 Google Sheets로 데이터를 공유. `owner` 필드('태일'/'정열' 문자열)로 필터링.

## 3. 데이터 구조 (현재 최종 상태 + 왜 이렇게 됐는지)

```
{
  id, name, category, memo,
  addresses: [ { id, label, address, detail, lat, lng, contactName, contactPhone } ],
  lat, lng, owner,
  logs: [ { type, date, memo, addressId } ],
  manualFolderId,
  createdAt
}
```

### 진화 과정 (왜 지금 구조인지)
1. 최초: `contacts[]`라는 전역 배열이 있고, 각 contact가 `addressId`로 특정 주소에 연결되거나(없으면 "공용").
2. v4.00: 데이터 분리(split)/병합(merge) 기능을 만들면서 주소별 필터링(`belongsToAddrFilter`)이 필요해짐 — 엑셀로 같은 고객사명+다른 주소를 가져오면 자동으로 "한 고객사, 여러 주소"로 묶이는데, 로그/연락처가 고객사 단위로만 공유되다 보니 주소(핀)별로 데이터가 안 갈라지는 문제가 있었음.
3. v5.00: `contacts[]` 완전 폐기. 담당자 정보(`contactName`/`contactPhone`)를 각 주소 블록 안으로 통합. "주소마다 담당자 1명"이 원칙이며, 주소와 담당자 둘 다 다르면 애초에 다른 고객사로 분리하는 게 원칙. 구버전 데이터는 `migrateContactsToAddresses()`가 앱 로드 시 자동 마이그레이션(addressId 있으면 해당 주소, 없으면 첫 번째 주소로 귀속).
4. "전체 공용 담당자" 개념은 v5.00에서 완전히 삭제됨 — 과거 문서에 남아있어도 무효.

### 담당자는 별도 식별자가 없음
컨택이력(`logs`)은 `addressId` 기준으로 저장되지, 담당자 고유ID 기준이 아님. "컨택은 담당자 기준이어야 한다"는 의견이 대화04에서 나왔으나, 이렇게 바꾸려면 데이터 모델 전체(담당자 고유ID 도입 등)를 바꿔야 하는 큰 작업이라 검토 후 보류함. 다른 기능(검색, 문자발송 연동)에도 영향이 갈 수 있음.

## 4. Google Apps Script 백엔드 (코드로는 안 보이는 사실)

- 구글시트를 행/열 DB로 안 쓰고, "데이터" 시트의 셀 A1 하나에 전체 데이터를 JSON 문자열로 통째로 저장하는 구조. index.html만 봐서는 알 수 없고 Apps Script 서버 코드를 직접 열어야 확인됨(대화04에서 clasp로 확인).
- 저장 방식은 원래 GET 쿼리 파라미터였다가, URL 길이 제한 문제로 form POST + 숨김 iframe 방식으로 전환됨(대화01).
- `SECRET_TOKEN`으로 인증(클라이언트 코드에 평문으로 박혀 있어 실질적 "비밀"로 기능하지는 않음 — 대화04에서 확인된 구조적 한계, 이번 범위 밖으로 인지만 하고 넘어감).
- 원래 동시 실행 잠금(LockService)이 전혀 없었음 — 대화04에서 새로 추가한 부분 업데이트(`appendLog`) 기능에만 적용함. 앞으로 서버에 쓰기 기능을 추가하면 반드시 같은 잠금을 공유해야 함.
- 한때 저장 후 검증 로직이 있었으나, 구글 API 간헐적 403 오류로 인한 오탐(정상 저장인데 실패로 오판) 문제로 제거함(대화01). 저장 검증을 다시 추가하자는 아이디어가 나오면 이 403 오탐 문제부터 해결 방법을 검토해야 함.
- 배포 흐름: `clasp push`(코드 갱신)만으로는 라이브 URL에 반영 안 됨. `clasp deploy -i <배포ID>`로 별도 배포해야 함. `clasp login`(브라우저 OAuth)과 `script.google.com/home/usersettings`의 "Google Apps Script API" 토글은 사람이 직접 해야 함(대화04).

## 5. 지도 화면 핵심 기능과 설계 배경

### 5-1. 핀 겹침 펼치기(spiderfy), 라벨 충돌 회피
미터 기반 계산에서 픽셀 기반 계산으로 재작성됨(대화02). 세부 이유는 이번 검색으로 완전히 확보되지 않았으니 필요시 대화02를 다시 검색할 것.

### 5-2. 같은 주소·다른 고객사 핀 병합 (4m 이내)
- 실거리 `ADDR_MERGE_M = 4m` 이내에 다른 고객사(같은 고객사의 다른 주소는 제외)가 있으면 핀 하나로 병합 표시.
- 병합 핀은 분류색 대신 중립 회색(`MERGED_PIN_COLOR`) — 합쳐진 업체들 분류가 제각각이라 색 섞으면 오히려 헷갈림.
- 클릭 시 `openMergedChooser()` 팝업으로 업체 선택. 이 팝업(`#merged-pin-overlay`/`#merged-pin-list`)은 "병합 핀 선택"과 "고객사 병합 확인" 두 가지 용도로 같은 DOM을 재사용 중 — 유지보수 시 헷갈리지 않게 주의할 것. (대화04에서 이 팝업이 뒤로가기 처리 등록에서 누락되어 버그가 난 적 있음 — 이 재사용 구조 때문에 놓치기 쉬웠을 가능성 있음.)

### 5-3. 클러스터링과 "유령 마커"
- 카카오 `MarkerClusterer` 사용, `minLevel: 9`, `gridSize: 38`(사용자 요청으로 기본값보다 작게 설정).
- 문제: 클러스터러는 "마커 개수"를 세는데, 병합 핀(여러 업체가 마커 1개)이 있으면 마커 개수 ≠ 실제 업체 수가 됨.
- 시도했다 버린 방법: 카카오 `texts` 콜백(숫자만 받고 마커 목록은 못 받는 API 제약으로 불가), `clustered` 이벤트로 텍스트 직접 덮어쓰기(카카오 개발자포럼에 보고된 "클릭 안 되는 버그"가 있어 위험해서 미채택).
- 채택한 방법: 병합 핀마다 화면에 안 보이는 1x1 투명 마커("유령 마커")를 (업체수-1)개 같은 위치에 추가해서, 클러스터러가 세는 마커 개수를 실제 업체 수와 일치시킴.
- 그리드 기반 클러스터링은 줌마다 격자가 새로 그어져 부모-자식 관계가 유지되지 않는 게 이 방식 특유의 공통 한계 — 버그 아님(사용자에게 이미 설명됨).

### 5-4. 데이터 분리(split)/병합(merge) — v4.00 신규, 대화04에서 병합 기능 확장
- 분리: 상세화면에서 "✂️ 분리" 버튼(주소 2개 이상일 때만 노출). 그 주소 전용(addressId 일치) 로그·연락처만 데리고 새 고객사로 분리, 공용(addressId 없음) 데이터는 원본에 남음. 새 고객사는 분류를 원본 그대로 복사, 메모는 비움.
- 병합(원형, 대화02): 정확히 2개 선택했을 때만 병합 버튼 노출. 대화04에서 2개 이상(N개)으로 확장됨 — 가장 먼저 선택한 고객사가 기준(이름 유지)이 되고 나머지를 흡수.
- 분류가 다르면 자동 규칙 없이 항상 사용자가 라디오 버튼으로 선택.
- 상세화면에서 주소별 필터링 가능(`selectDetailAddress()`, `belongsToAddrFilter()`). 핀을 클릭해서 들어가면 그 핀의 주소가 자동 선택된 채로 열림.

### 5-5. 컨택기록 입력 시 주소 선택
고객사 선택 시 주소가 2개 이상이면 "어느 주소 건인가요?" 드롭다운 표시(1개면 안 물어보고 공용 기록). 검색 결과에서 주소가 2개 이상인 고객사는 "업체명 · N개 주소"로 축약 표시 후 클릭 시 주소 목록 아코디언 펼침.

### 5-6. 폰에서 지도 백색 화면 문제
bfcache(뒤로가기 캐시) 복원 시 `kakao.maps.event.trigger`의 resize를 여러 타이밍에 반복 호출하는 방식으로 부분 완화함(대화01, 완전 해결은 아님 — "부분 완화"라고 명시돼 있었음).

### 5-7. 네이버 인앱브라우저
감지 배너가 있음(대화01부터). 대화04에서 위치 정보(Geolocation) 관련 문제를 조사했을 때, 실제 원인은 인앱브라우저 자체 문제가 아니라 당시 커스텀 도메인이 HTTP로 서빙되고 있었기 때문으로 최종 확인됨(HTTPS 적용 후 해결). 다만 인앱브라우저 자체의 제약 가능성도 완전히 배제되지는 않음 — "다른 브라우저로 열기" 안내가 실용적 우회책으로 유지되고 있음.

### 5-8. 그 외 대화01~02에서 이어받은 기능 (대화03 문서의 요약 목록 기준, 상세 미확인)
- **엑셀 가져오기(SheetJS)**: 컨택유형이 불명확한 행은 임의 기본값을 넣지 않고 건너뜀(원칙: 애매하면 건너뛰고 사람이 원본에서 직접 수정).

## 6. 폴더/목록 화면 (v5.00 이후, 대화03·04)

### 버전 관리 규칙 (대화03에서 명시적으로 확정된 규칙)
- 정수부(메이저): 구조적으로 큰 변화(데이터 모델 전면 개편 등) → +1
- 소수점 첫째자리: 중간 규모 기능 추가 → +0.1 (표기는 반드시 v5.0이 아니라 v5.00처럼 2자리 고정)
- 소수점 둘째자리: 자잘한 수정·버그픽스 → +0.01
- 매 작업마다 버전을 올려야 하며, 작업 시작 시 반드시 현재 버전(설정 화면 헤더 표시) 확인 후 진행할 것.

- 같은 고객사명끼리 자동으로 폴더로 묶여 표시(기본 접힘 상태). 폴더 상태는 `listFolderState` 객체로 관리.
- 대화04에서 사용자가 직접 만드는 수동 폴더 기능 신규 추가: 생성/이름수정/해체/삭제 가능. 길게 눌러 선택 후 상단 "폴더" 버튼으로 지정. 폴더 자체를 길게 누르면 이름수정/해체(고객사는 남김)/삭제(고객사까지 휴지통 이동) 메뉴.
- **"위와 동일한 담당자" 체크박스(v5.01)**: 고객사 등록/수정 폼에서 두 번째 주소 블록부터 하단에 표시됨. 체크하면 바로 위 주소의 담당자명·전화번호를 그대로 복사해 채우고 해당 입력란은 비활성화(회색 처리). 체크 해제하면 필드 초기화 및 재활성화.
- 검색창 동작(v5.01, 대화03에서 변경): 검색 결과 선택 시 상세화면을 안 열고 지도 핀 위치로 이동만 함. 주소 여러 개면 결과에서 고객사명 클릭 시 주소 목록 아코디언 펼침.
- 실제 운영 분류(category) 7개: 계약 중 / 친밀 / 보통 / 소원 / 발굴·가망 / 거점 / 미분류. 코드의 `DEFAULT_CATEGORIES`(초기 시드값)와 실제 운영 분류는 다르므로 혼동 주의. "미분류"는 `UNCATEGORIZED_ID`(`cuc`)로 고정, 삭제 불가.
- 다중 분류(태그형) 시스템은 의도적으로 보류 중(대화03부터, 대화04까지 유지).

### v4.02 버그 수정 이력 (대화03)
- **"지도에서 보기" 선택 주소 미반영 버그**: 상세화면에서 특정 주소를 선택하고 "지도에서 보기"를 눌러도 대표 첫 주소로 이동하던 버그. 원인은 `moveToMarker(id)` 함수가 `addressId` 인자를 안 받았기 때문. `moveToMarker(id, addressId)`로 수정해 해당 주소 좌표로 이동하도록 고침.
- **네비게이션 전단계 회귀 버그**: 목록→상세→수정→저장/취소 흐름에서 전단계(상세 또는 목록)로 안 돌아가고 전부 꺼지던 버그. `closeFormSheet()`, `closeDailySheet()` 함수와 `dailySheetOrigin` 변수를 추가해 어디서 열렸는지 추적하고 그 자리로 복귀하도록 수정.

## 7. 엑셀 가져오기/내보내기 (대화04에서 전면 재설계, 가장 큰 작업)

### 최종 구조
- "고객사 정보 내보내기" 버튼으로 받은 파일 안에 시트 2개:
  - "기존 고객사": 숨김 열(`_고객사ID`/`_주소ID`/`_체크섬`) 포함, 수정·삭제 전용.
  - "신규 추가": 숨김 ID 없음, 컨택이력 컬럼(컨택날짜/유형/메모) 포함, 추가 전용.
- "고객사 정보 가져오기" 버튼으로 재업로드하면 두 시트를 각각 다르게 처리해 미리보기(추가/수정/삭제/충돌/이름중복)에 표시, 체크한 것만 반영.
- "엑셀 양식 다운로드" 버튼은 제거됨 — "고객사 정보 내보내기"로 받은 파일이 최초 입력용 양식 역할도 겸하기 때문.
- 컬럼 순서(양쪽 시트 통일): 고객사명-소유자-분류-담당자명-담당자 전화번호-주소구분-주소-상세주소-메모-컨택날짜-컨택유형-컨택메모. 그룹 경계에 세로 구분선(테두리 아님).

### 시도했다 버린 방법
- 처음엔 신규/기존을 한 시트에서 같이 처리(숨김 ID 있으면 수정, 없으면 신규)했으나, 사용자가 기존 행을 지우지 않고 다른 회사 정보로 덮어쓰거나 보이는 칸만 비우는 경우 위험이 있어 두 시트 완전 분리로 교체.
- "이름이 완전히 다른 값으로 바뀌면 경고 표시" 방안도 검토했으나, 시트 분리로 그 상황 자체가 구조적으로 발생하지 않게 되어 폐기.
- 컨택이력 컬럼을 신규 등록에서 완전 제거했다가, "신규 등록 = 실제 신규 거래처"가 아니라 "이제 막 앱에 입력하는 기존 거래처"인 경우가 많다는 게 확인되어 재도입.

### 세부 규칙
- 완전 공백 행 처리("기존 고객사" 시트): 숨김 ID는 있지만 보이는 칸 전부 빔 = 그 주소(또는 무주소 고객사면 고객사 전체) 삭제 의도. 판단 단위는 행. 값 하나라도 남으면 일반 수정으로 처리.
- "기존 고객사" 시트의 컨택이력: 각 주소 행에 그 주소의 최근 이력을 채워 보여줌. 값 유지=중복 안 됨(체크섬 포함), 값 비움=이번엔 안 남김(삭제 아님), 값 변경=새 이력 추가(누적, 절대 삭제 안 함).
- 이름 중복 감지: 공백·띄어쓰기 차이 무시하고 비교(완전일치보다 안전한 기준). 겹치면 "이름 중복" 그룹으로 분류, "그래도 새로 추가" 또는 "기존 고객사에 주소만 추가" 선택.
- 소유자 필터 반영: 내보내기 시 지도 화면의 소유자 필터(전체/나/상대방)를 반영. 필터링된 상태로 내보내도 재가져오기 시 필터 밖 고객사가 삭제 후보로 잘못 잡히지 않도록 메타 스냅샷도 필터 범위 기준으로 만듦(검증 완료).
- 디자인: 안내 시트는 카드형 박스(섹션 병합+테두리), 데이터 시트는 헤더+첫 열 틀고정, 셀 테두리, Notion 색상 팔레트만 참고(#F7F6F3/#0075DE/#37352F — CSS 스타일 완전 재현은 Excel 특성상 불가능).
- 버그: 데이터 없는 컬럼의 헤더 자체가 사라지는 버그 발견 → "컬럼 생성 로직"과 "폭 계산 로직" 분리로 수정(재현은 코드상 어려웠으나 실제 렌더링에서는 발생 확인됨).

### 관련 기능
- JSON 전체 백업/복원("데이터 내보내기"/"데이터 가져오기", 설명: "전체 고객사 데이터를 JSON 파일로 저장/복원") — 엑셀 기능과 별개, 전체 덮어쓰기 용도. 복원 시 원래 확인 팝업이 없었던 안전 문제를 발견해 추가함.
- 컨택 리마인드 알림 설명: "설정한 일수 이상 미컨택 시 알림".

## 8. 뒤로가기(모바일/PWA) 처리 (대화04 신규 구현)

- 열린 화면을 하나씩 닫아가며 뒤로가기 처리, 더 닫을 게 없으면 종료 확인 팝업.
- 새 팝업/시트를 추가하면 `closeTopmostLayer()`와 `pushNavGuard()` 두 곳에 반드시 등록해야 함 — 실제로 병합핀 팝업(`merged-pin-overlay`, 5-2 참고)에서 이 등록이 빠져 뒤로가기가 먹통이 되는 버그가 났었고 수정됨.
- 웹 기술로는 "뒤로가기 시 즉시 종료"가 원천적으로 불가능 — "종료" 확인 후 `history.back()`을 자동으로 한 번 시도하는 정도까지만 가능. 실제 갈 곳(브라우저 히스토리)이 있어야 화면을 벗어남. 히스토리가 얕으면(홈 화면에서 방금 열었을 때 등) "종료" 눌러도 반응 없는 게 정상.
- 삭제 등 확인이 필요한 동작에 브라우저 기본 `confirm()`을 안 쓰고 `showGenericConfirm()` 같은 자체 팝업을 쓰는 방침(최초 계기였던 "인앱브라우저가 confirm() 차단" 진단은 틀린 것으로 확인됐으나, 방어적 차원에서 방침은 유지).

## 10. GitHub 연동 (대화04)

- 기존엔 파일 다운로드 후 GitHub 웹사이트에 직접 업로드하는 방식이었음. Git + GitHub CLI 설치, 기존 저장소(`gtale4102/coway-map`)와 로컬 폴더(그동안 git 미관리 상태였음) 연결 완료.
- 로컬 프로젝트 폴더가 실제 배포본과 다를 수 있음 — 작업 방식이 "다운로드 후 직접 업로드"였기 때문에 로컬에 결과물을 복사해 넣은 적이 없었음. 실제로 아이콘 파일 두 개가 로컬/원격에서 달랐고, GitHub 버전이 최신(실제 배포된 디자인)임을 사용자가 직접 확인 후 정리함.
- 이 저장소는 public이므로 개인정보·비밀값 포함 파일은 커밋 전 반드시 확인해야 함:
  - 프로젝트 폴더 내 Google Cloud 서비스 계정 키 파일 발견 — 실사용처 불명, 과거 노출 이력 없음(전체 커밋 스캔 확인) → 삭제·로테이션 안 하고 로컬 보관만, `.gitignore`로 커밋 제외.
  - 인수인계 md 파일 5개에 카카오 API 키 평문 포함 → 레닥션 후 커밋.
  - 핀 라벨 렌더링 디버그 이미지 3개에 실제 라이브 고객사 데이터가 그대로 담겨있어(46건 중 24건 실명·주소 일치 확인) 커밋에서 제외.
  - `apps-script/` 폴더는 이번엔 제외(별도 관리 대상).
- clasp(Apps Script CLI) 설정: `clasp login`(브라우저 OAuth, 사람이 직접), Apps Script API 토글 활성화(계정 소유자가 직접) 필요.

## 13. 그 외 알아야 할 실전 함정 (요약)

- 파비콘 캐시는 일반 브라우저 캐시와 별개 관리됨.
- GitHub Pages 커스텀 도메인: DNS 확인 성공 ≠ SSL 인증서 즉시 발급, 그 사이엔 Enforce HTTPS 못 켬. 커스텀 도메인 등록 시 기존 github.io 주소가 자동 리다이렉트됨.
- **GitHub Pages 배포 실패 시**: 서버 성능 저하(githubstatus.com에서 "Degraded Performance" 확인 가능)로 인한 일시적 실패일 수 있음 — Actions 탭에서 "Re-run failed jobs"로 재시도하면 되는 경우가 많음(대화03, 대화04에서도 유사 사례 재확인됨).
- Geolocation API는 HTTPS 필수 — HTTP면 권한 팝업도 없이 조용히 실패.
- Claude Code에 60초 무응답 시 자동 진행하는 동작(AFK 모드, 비공식) 있음 — 실제 이 프로젝트에서 두 번 발생. 대응 원칙: 무응답 시 보수적 선택 + 다음 보고에 명시. 환경변수 `CLAUDE_AFK_TIMEOUT_MS`로 억제 가능(비공식).
- Excel(ExcelJS) 스타일링은 CSS 재현 불가(그림자·그라데이션·웹폰트 등), 색상 팔레트 적용까지만 가능.
- Cowork 세션 진행 시, 그 원본 대화는 이후 claude.ai 채팅에서 검색으로 재구성 불가능함(대화03이 그 사례) — 중요한 결정/이유는 반드시 그때그때 인수인계 문서로 별도 남겨야 함.
- Grep 도구로 한글 패턴 검색 시 매칭 실패할 수 있음(대화03) — bash grep이나 python3으로 우회.
- Cowork bash 워크스페이스가 가끔 다운됨(대화03) — Read/Edit 파일 도구로 직접 작업 전환 가능.
- **대화03 시점 작업 방식 메모(현재는 대화04에서 git 연동으로 일부 해소됨)**: 과거엔 "Claude는 GitHub에 직접 접근 불가 → 코드 수정 후 파일 다운로드해서 직접 push"가 원칙이었음. 대화04에서 Git+GitHub CLI 연동을 완료해 Claude Code가 직접 git push까지 할 수 있게 됐으므로, 이 옛 제약은 더 이상 유효하지 않음 — 다만 "확인 안 받고 작업 진행 금지"("어때?"처럼 의견만 묻는 질문에 바로 코드 작업하면 안 됨, 지시와 의견 질문을 명확히 구분해서 응답할 것) 원칙 자체는 계속 유효함.
