# 통합설계 참고 (대화01) — 코드만 봐서는 알 수 없는 정보

> 최종 index.html을 읽으면 알 수 있는 내용은 제외하고, 결정 배경·실패 이력·함정·원칙만 수록.

---

## 1. 시도했다가 실패해서 버린 방법과 이유

### 1-1. 저장 방식: GET 쿼리 파라미터 → POST로 전환
- **버린 방법**: 저장 데이터를 URL 쿼리 파라미터에 담아 Apps Script doGet()으로 전송하는 JSONP 저장 방식
- **실패 원인**: 고객사 수가 늘어날수록 JSON이 커져 URL 길이 제한에 걸림. 제한 초과 시 브라우저나 중간 인프라에서 요청 자체를 조용히 버리거나 잘라내 **데이터가 누락되지만 오류 없이 성공한 것처럼 보였음**. 정열님이 입력한 고객사 20~30개가 이 방식으로 소실된 사고의 실질적 원인 중 하나.
- **대체**: form(POST) + 숨김 iframe 방식. URL에 데이터를 넣지 않으므로 용량 제한 없음.

### 1-2. 저장 후 검증(verification) 로직
- **버린 방법**: 저장 완료 후 곧바로 doGet으로 다시 읽어 저장된 customer ID가 전부 존재하는지 확인하는 로직. 실패 시 최대 3회 재시도 + 최종 실패 시 사용자에게 경고.
- **실패 원인**: 구글 Apps Script의 응답 경유 도메인(`script.googleusercontent.com`)에서 단시간 반복 호출 시 간헐적 403이 발생함. 저장 자체는 성공했는데 검증 GET이 403을 받아 "저장 실패" 경고가 뜨는 오탐(false alarm)이 반복됨. 사용자 입장에서 매번 "저장 확인 실패" 메시지가 떠 불신과 불편을 유발.
- **현재 방침**: 검증 없음. 저장 요청 후 바로 진행. 데이터 안정성은 POST 방식(용량 문제 없음) + 병합 + tombstone으로 구조적으로 확보.
- **🔴 재도입 금지**: 이미 시도 → 부작용 확인 → 제거한 이력이 있음. "저장이 됐는지 확인해야 하지 않냐"는 제안은 이 이유로 거절해야 함.

### 1-3. 경로 히스토리 삭제 잠금(lock) 방식
- **버린 방법**: `isRouteHistSaving` 플래그로 저장 완료 전까지 다음 삭제를 차단하는 방식
- **실패 원인**: 연타로 경로를 지우려 하면 첫 번째 삭제가 완료될 때까지 기다려야 해 UX가 나쁘다는 피드백
- **대체**: tombstone만으로 충분. `markRouteHistDeleted(id)`는 동기적 localStorage 쓰기이므로 연타해도 tombstone이 순서대로 즉시 기록됨 → 이후 비동기 병합이 어떻게 겹쳐도 모두 되살리기 차단됨.

### 1-4. 고객사 삭제 시 백업 후 롤백 방식
- **버린 방법**: `const backup = customers`로 배열을 백업해두고, 저장 실패 판정 시 `customers = backup`으로 롤백하는 방식
- **실패 원인**: (1-2)의 검증 제거로 "저장 실패" 판정 자체가 없어졌으므로 함께 제거. 또한 `const backup = customers`는 참조 복사라서 백업 역할을 못 하는 구조적 오류도 있었음.

### 1-5. GitHub 저장소 Private 전환
- **버린 방법**: 소스코드 노출 방지를 위해 GitHub 저장소를 private로 전환하는 방안
- **실패 원인**: GitHub Pages 무료 개인 계정은 public 저장소에서만 작동. private로 전환하면 GitHub Pages 사용 불가. 또한 private 저장소라도 배포된 사이트 자체는 public이어서 페이지 소스 보기로 코드 확인 가능 → 근본 해결 불가.

### 1-6. isMobile 변수를 initMap() 내부에서 const로 선언
- **버린 방법**: `function initMap() { const isMobile = /Android.../i.test(...); ... }`
- **실패 원인**: 함수 스코프에 갇혀 `toggleRoutePanel()`, `setOriginGPS()` 등 외부 함수에서 접근 불가. 결과적으로 폰에서 "PC에서는 현위치를 사용할 수 없습니다" 메시지가 뜨는 버그 발생.
- **대체**: 전역 변수로 선언, 변수 선언 시점에 바로 초기화(`let isMobile = /Android.../i.test(navigator.userAgent);`)

## 2. 반드시 지켜야 하는 제약·원칙

### 2-1. 🔴 Tombstone 패턴 — 가장 중요
**삭제 관련 기능을 추가하거나 수정할 때는 반드시, 배열에서 항목을 제거하기 전에 tombstone 기록 함수를 동기적으로 먼저 호출해야 한다.**

```
markDeleted(id)          // customer 단건 삭제 시
markManyDeleted(ids)     // customer 다중 삭제 시
markRouteHistDeleted(id) // routeHistory 삭제 시
```

**배경**: `mergeAndSaveToSheet()`는 "원격에 있는데 로컬에 없는 항목 = 다른 사람이 방금 추가한 것"으로 해석해서 로컬에 push한다. 삭제 후 tombstone 기록 없이 저장하면, 저장 직전 병합 단계에서 방금 삭제한 항목이 원격 스냅샷으로부터 되살아난다. 이것이 정열님 고객사 20~30개 소실 사고의 근본 원인이었다.

### 2-2. Tombstone은 삭제 전(前), 동기적으로
tombstone 기록과 배열 수정이 아래 순서를 따라야 한다:

```js
// ✅ 올바른 순서
markDeleted(id);                           // 1. tombstone 기록 (동기, 즉시)
customers = customers.filter(...);          // 2. 로컬 배열 수정
await saveData();                           // 3. 저장 (비동기 - 내부에서 merge 발생)

// ❌ 잘못된 순서 — 부활 버그 재발
customers = customers.filter(...);          // 1. 먼저 제거
markDeleted(id);                           // 2. tombstone (이미 늦음 — merge fetch가 먼저 실행될 수 있음)
await saveData();                           // 3. merge 단계에서 이미 되살아날 수 있음
```

### 2-3. 미분류(id: 'cuc')는 항상 존재해야 함
- `ensureUncategorized()` 함수가 loadData() 완료 후 호출되어 보장
- 새로운 데이터 로딩 경로(예: 가져오기 기능 수정)를 추가할 경우 반드시 `ensureUncategorized()` 호출을 포함해야 함
- 이 id는 엑셀 가져오기 시 분류 미매칭 고객사의 기본값이므로, 존재하지 않으면 해당 고객사들이 분류 없이 뜨거나 오류 발생

### 2-4. Apps Script 파일 수정 후 반드시 "새 버전" 재배포
- Apps Script를 수정하고 저장(Ctrl+S)만 하면 이전 배포 버전이 계속 실행됨
- 배포 → 배포 관리 → 연필 아이콘 → 버전: "새 버전" → 배포 순서를 반드시 거쳐야 함
- 새 배포를 만들면 URL이 바뀌므로 반드시 기존 배포를 "편집"(연필 아이콘)해야 URL 유지

### 2-5. 파일 생성 원칙 (사용자 선호)
"만들어줘" / "진행해줘" 명시 전까지 index.html 파일 생성 금지. 방향 검토 → 승인 → 작업 순서를 지켜야 함. 무단 생성은 토큰 낭비 문제로 실제 항의를 받은 이력 있음.

## 3. 설정 과정에서의 함정과 실전 지식

### 3-1. form POST 응답의 신뢰 불가
- `saveToSheetViaForm()`은 iframe의 `onload` 이벤트로 저장 완료를 감지하지만, `onload`는 성공/실패를 구분하지 않음
- Apps Script의 응답은 `script.googleusercontent.com`으로 리다이렉트 되어 반환되는데, 이 도메인에서 단기 반복 호출 시 간헐적 403이 발생 (실제 저장 성공 여부와 무관한 인프라 이슈)
- 이 때문에 응답 내용으로 성공/실패를 판단하는 것이 구조적으로 불안정함 → (1-2)의 검증 로직 폐기 배경

### 3-2. doPost에서 e.parameter 사용
Apps Script doPost()에서 form-urlencoded 요청의 body 파싱:

```js
// ✅ 올바른 방법 (form-urlencoded body)
e.parameter.payload    // form 필드로 전송된 값

// ❌ 틀린 방법
e.postData.contents    // 이건 raw body string (JSON body일 때 사용)
```

form POST로 전송했는데 `e.postData.contents`를 쓰면 payload가 null로 들어와 저장이 조용히 실패함.

### 3-3. 카카오맵 컨테이너 크기 0 → 타일 깨짐
- 레이아웃이 확정되기 전에 `new kakao.maps.Map(container, options)` 실행 시 컨테이너 크기를 0으로 인식
- 증상: 지도 배경이 하얀 화면이거나 "kakao map" 텍스트가 타일처럼 반복되는 패턴
- 해결: `initMap()` 직후 50, 200, 500, 1000ms 타이머로 `kakao.maps.event.trigger(map, 'resize')`를 4회 반복 호출
- 특히 안드로이드 폰에서 뒤로가기 → 재진입(bfcache 복원) 시 자주 발생

### 3-4. bfcache에서는 load 이벤트가 재발화하지 않음
- 안드로이드 폰에서 뒤로가기로 앱 종료 후 재진입하면 브라우저가 페이지를 bfcache에서 복원
- 이때 `window.addEventListener('load', ...)` 핸들러는 실행되지 않음
- `pageshow` 이벤트는 bfcache 복원 시에도 발화함 (`event.persisted === true`로 구분 가능)
- 지도 resize 재트리거를 `pageshow`에도 걸어야 하는 이유

### 3-5. 카카오모빌리티 길찾기 API CORS 제한
- `https://apis-navi.kakaomobility.com` 직접 fetch 호출은 브라우저 CORS 정책으로 차단될 수 있음
- 현재 코드는 fetch 실패를 try-catch로 잡아 직선(점선) 경로 fallback 처리
- 일부 환경에서는 허용될 수 있으나 불안정하므로 신뢰하지 말 것

### 3-6. JSONP 콜백 이름 충돌 방지 필수
- fetchSheetData() 등 JSONP 방식 호출 시 콜백 함수명을 `Date.now() + Math.random()` 조합으로 생성
- 단순히 `Date.now()`만 쓰면 1ms 이내 중복 호출 시 콜백 이름 충돌로 응답이 잘못 처리될 수 있음

### 3-7. 구글 시트 셀 용량 한계 잠재적 위험
- 현재 전체 데이터(customers + categories + routeHistory + trash)를 A1 셀 하나에 JSON 문자열로 저장
- Google Sheets 단일 셀 문자열 한도는 50,000자
- 고객사 수백 개 + 컨택 이력 다수 + trash 미정리 상태가 겹치면 초과 가능성 있음 (아직 미발생)
- 주기적으로 trash 비우기를 권장, 또는 향후 시트 구조 재설계 고려

### 3-8. 병합 로직의 구조적 한계
- mergeAndSaveToSheet()의 병합은 "동시 추가" 충돌 방지에는 효과적이나, "동시 수정"(양쪽에서 같은 고객사 정보를 다르게 수정) 충돌은 해결하지 못함 → 마지막 저장이 이김(last-write-wins)
- 두 명이 같은 고객사를 동시에 수정하는 경우는 실제 사용 패턴상 거의 없으므로 허용 가능한 수준으로 판단하고 방치

### 3-9. Apps Script 배포 URL 유지 조건
- Apps Script 배포 편집(기존 배포의 연필 아이콘 → 새 버전)을 하면 URL 변경 없음
- 기존 배포를 삭제하고 새 배포를 만들면 URL이 완전히 새 주소로 바뀜 → 코드 내 SHEET_URL 수정 + GitHub 재배포 필요
- 실수로 새 배포 생성 시 데이터 접근 불가 상태가 됨

### 3-10. 인앱 브라우저 파일 첨부 제한 — 코드로 해결 불가
- 네이버 앱, 카카오톡 등 인앱 브라우저는 `<input type="file">`을 아예 차단하는 경우가 있음
- `<label for>` 방식(현재 적용)이 JS `.click()` 방식보다 더 범용적이나, 보안 정책으로 막힌 경우엔 이것도 소용 없음
- 유일한 해결책: 외부 브라우저(삼성 인터넷, 크롬)에서 열기 → UA 감지 배너로 안내 중
