# 통합설계 참고 (대화04) — 코드만으로는 알 수 없는 정보

이 문서는 코웨이 B2BC 고객사 지도 앱 관련 작업(엑셀 가져오기/내보내기 재설계, 폴더 기능, 뒤로가기 처리, 저장 속도 개선, GitHub 연동 등) 과정에서 나온 정보 중, 최종 코드 파일만 읽어서는 알 수 없는 내용만 정리한 것입니다. 코드를 보면 바로 알 수 있는 내용(함수 이름, 로직 자체)은 제외했습니다.

---

## 1. 시도했다가 실패해서 버린 방법과 이유

### 1-1. 아이콘 핀 모양 — 겹치는 원으로 이음매 만드는 방식
머리(원)와 꼬리(삼각형) 사이 이음매를 매끄럽게 하려고, 그 자리에 별도의 보조 원을 하나 더 겹쳐 그리는 방식을 처음 시도했습니다. 그런데 그 보조 원의 반지름이 머리 원의 그 높이에서의 실제 폭보다 넓어서, 핀 옆면이 불룩 튀어나오는 결과가 나왔습니다. 이후 보조 원을 없애고, 원의 방정식으로 정확한 폭을 계산해 삼각형 밑변이 원 경계선 위에 정확히 오도록 하는 방식으로 교체했습니다. 다음에 유사한 도형(핀, 말풍선 등)을 만들 때, 원과 다각형을 이어붙이는 이음매는 반드시 원의 실제 폭(코드상 `r * sqrt(1 - f²)` 같은 공식)을 계산해서 맞춰야지, 임의의 반지름으로 보조 도형을 겹치면 튀어나오는 문제가 생깁니다.

### 1-2. 엑셀 파일에 Notion 스타일 전체 적용
"노션 스타일 그대로 적용해달라"는 요청이 있었으나, Excel(ExcelJS)은 HTML/CSS와 렌더링 방식 자체가 달라 그림자·둥근 모서리·그라데이션·웹폰트·호버 효과를 구현할 방법이 없습니다. 색상 팔레트(배경 `#F7F6F3`, 포인트 `#0075DE`, 텍스트 `#37352F`)만 셀에 적용하는 선에서 타협했습니다. 앞으로도 "엑셀/스프레드시트를 특정 웹 디자인처럼 만들어달라"는 요청이 오면, 색상 팔레트 적용까지만 가능하고 그 이상은 기술적으로 불가능하다는 점을 먼저 안내해야 합니다.

### 1-3. 엑셀 가져오기 — 신규/기존을 한 시트에서 같이 처리하는 방식
처음엔 하나의 시트에서 숨김 ID가 있으면 수정, 없으면 신규로 처리하는 단일 시트 구조였습니다. 그런데 이 구조에서는 사용자가 기존 행을 지우지 않고 그 자리에 다른 회사 정보로 덮어쓰거나(숨김 ID가 남아있어 엉뚱한 고객사가 수정되는 결과), 보이는 칸만 비우고 숨김 ID는 남겨두는 경우(의도치 않게 "이름을 공백으로 바꾸는 수정"으로 처리됨) 위험이 있었습니다. 이를 근본적으로 막기 위해 "기존 고객사"(숨김 ID 있음, 수정·삭제 전용)와 "신규 추가"(숨김 ID 없음, 추가 전용) 두 시트로 완전히 분리하는 구조로 교체했습니다. 이 과정에서 "이름이 완전히 다른 값으로 바뀌면 경고 표시"라는 방안도 검토했었으나, 시트 분리로 그 상황 자체가 구조적으로 발생하지 않게 되어 폐기했습니다.

### 1-4. 컨택이력 컬럼 — 제거했다가 재도입
신규 등록용 엑셀에서 컨택이력(컨택날짜/유형/메모) 컬럼을 처음엔 완전히 제거했습니다(신규 고객사는 과거 이력이 없을 것이라는 전제). 그런데 실제로는 "이제 막 앱에 입력하는 것"과 "실제로 오래된 기존 거래처인 것"이 다르다는 게 확인되어(이미 거래해온 고객사를 이제 데이터베이스에 입력하는 초기 단계), 과거 이력을 등록 시점에 같이 넣고 싶은 실사용 니즈가 있었습니다. 그래서 다시 컨택이력 컬럼을 넣는 것으로 최종 결정했습니다. "신규 등록 = 실제로 신규 거래처"라고 단정하면 안 됩니다.

### 1-5. 폴더 항목 이동 — 드래그 앤 드롭 방식
고객사를 폴더로 옮길 때 드래그 앤 드롭으로 구현하려 했으나, 목록의 각 항목에 이미 "길게 누르면 선택 모드 진입"이라는 제스처가 있어서 드래그 제스처와 충돌 위험이 있었습니다. 그래서 드래그 대신 "길게 눌러 선택 → 상단 버튼으로 폴더 지정" 방식으로 대체했습니다. 같은 화면 요소에 길게 누르기(long-press) 제스처를 두 가지 용도로 동시에 쓰려고 하면 충돌하니 주의가 필요합니다.

### 1-6. 폴더 삭제 버그 — 잘못된 최초 진단
폴더를 삭제해도 다시 나타나는 버그가 있었을 때, 처음엔 "브라우저 기본 확인창(`confirm()`)이 일부 인앱브라우저에서 차단되는 문제"로 진단하고 커스텀 팝업으로 교체했습니다. 그런데 이 진단은 틀렸고, 실제 원인은 삭제 시 삭제기록(tombstone)을 안 남겨서 서버 병합 시 되살아나는 것이었습니다(아래 2-1 참고). 커스텀 팝업 교체 자체는 유지했지만(방어적으로 나쁘지 않은 선택), 근본 원인은 다른 곳에 있었습니다.

### 1-7. 담당자 기준 컨택이력 재설계 — 검토 후 보류
"컨택은 담당자 기준이어야 한다"는 의견이 나와 검토했으나, 현재 데이터 구조상 담당자는 별도 식별자가 없는 주소에 딸린 텍스트일 뿐이라, 담당자 기준으로 바꾸려면 데이터 모델 자체(담당자 고유ID 도입, 컨택이력이 주소가 아니라 그 ID를 참조하도록 변경)를 바꿔야 하는 큰 작업입니다. 다른 기능(검색, 문자발송 연동)에도 영향이 갈 수 있어 이번 범위에서 보류하고, 지금 구조(주소 기준)를 그대로 유지하기로 했습니다.

## 2. 반드시 지켜야 하는 제약·원칙

### 2-1. 삭제 가능한 컬렉션은 전부 삭제기록(tombstone)이 있어야 함
이 앱의 로컬↔구글시트 동기화는 "병합 시 상대방에만 있는 항목은 추가만 하고, 삭제는 안 함"이 기본 방식입니다. 그래서 삭제가 가능한 모든 컬렉션(customers, routeHistory, manualFolders, 휴지통 완전삭제 등)은 각각 별도의 삭제기록 목록(`markXDeleted()` / `loadDeletedXIds()` 패턴)이 있어야만 삭제가 병합 시 되살아나지 않습니다. 새로운 삭제 가능 기능을 추가할 때마다 이 패턴을 빠뜨리지 않고 복제해야 합니다. 실제로 이번 작업에서 폴더 기능과 휴지통 완전삭제 두 곳에서 이 패턴을 빠뜨려 버그가 났습니다.

### 2-2. 새 팝업/화면을 추가하면 뒤로가기 처리 목록에도 반드시 등록해야 함
뒤로가기 버튼 처리는 `closeTopmostLayer()`(열린 화면을 순서대로 확인해 닫는 함수)와 `pushNavGuard()`(화면 열 때 히스토리에 가드를 쌓는 함수) 두 곳에 모든 팝업/시트가 등록되어 있어야 정상 작동합니다. 새 팝업이나 시트를 추가할 때 이 두 곳에 등록을 빠뜨리면, 그 화면에서만 뒤로가기가 먹통이 되는 버그가 생깁니다(실제로 병합핀 팝업에서 이 등록이 빠져 있었음).

### 2-3. 뒤로가기로 "즉시 종료"는 웹 기술로 원천적으로 불가능
JS로 브라우저 탭이나 PWA를 즉시 강제 종료하는 방법은 없습니다. "종료" 확인 후에는 `history.back()`을 자동으로 한 번 시도하는 정도까지만 가능하며, 실제로 갈 곳(브라우저 히스토리)이 남아있어야 화면을 벗어납니다. 히스토리가 얕은 상태(홈 화면에서 새로 열었을 때 등)에서는 "종료"를 눌러도 반응이 없는 게 정상이며, 이는 코드로 고칠 수 없는 한계입니다.

### 2-4. 브라우저 기본 confirm()/alert() 대신 자체 팝업 사용
이 앱은 삭제 등 확인이 필요한 동작에 브라우저 기본 `confirm()`을 쓰지 않고 `showGenericConfirm()` 같은 자체 팝업을 쓰는 방침을 갖고 있습니다. (최초 계기였던 "인앱브라우저가 confirm()을 차단한다"는 진단 자체는 틀린 것으로 확인됐지만, 방어적 차원에서 이 방침은 유지하기로 했습니다.)

### 2-5. 이름 중복 판단은 공백/띄어쓰기 차이를 무시
신규 고객사 이름이 기존 고객사와 겹치는지 판단할 때, 완전 일치가 아니라 앞뒤 공백·띄어쓰기 차이를 무시하고 비교합니다. 이유는 "실제 중복을 놓치는 것"(예: "코웨이"와 "코웨이 "를 다른 회사로 오판)이 "다른 회사인데 확인창이 한 번 더 뜨는 것"보다 훨씬 손해가 크다는 판단 때문입니다.

### 2-6. 완전 공백 행 = 삭제 의도로 판단 ("기존 고객사" 시트 한정)
숨김 ID가 있는 행에서, 보이는 칸이 전부 비어있으면 "그 주소(또는 고객사)를 삭제하려는 의도"로 판단합니다. 판단 단위는 행(주소) 단위이며, 값이 하나라도 남아있으면 삭제가 아니라 일반 수정으로 처리합니다.

### 2-7. 이 저장소(coway-map)는 public
GitHub 저장소가 공개 상태이므로, 실제 개인정보(고객사명·전화번호·주소)나 비밀값(API 키, 서비스 계정 키)이 담긴 파일은 커밋 전 반드시 내용을 확인해야 합니다. 실제로 인수인계 md 파일들에 카카오 API 키가 평문으로 있어 레닥션 후 커밋했고, 핀 라벨 렌더링 테스트 이미지에 실제 고객 데이터가 있어 커밋에서 제외했습니다.

## 3. 설정 과정에서의 함정과 실전 지식

### 3-1. 파비콘 캐시는 일반 브라우저 캐시와 별개
파비콘(탭 아이콘)은 일반 "캐시 삭제"로 안 지워지는 경우가 흔합니다. 실제 파일은 서버에 정상 반영됐는데도 파비콘만 옛날 것으로 남아있을 수 있으며, 이는 코드나 배포 문제가 아니라 브라우저의 별도 캐시 문제입니다.

### 3-2. GitHub Pages 커스텀 도메인 설정 시 순서 함정
DNS 확인(check)이 성공해도 SSL 인증서가 바로 발급되는 것은 아니며, 그 사이 기간에는 "Enforce HTTPS"를 켤 수 없습니다. 또한 커스텀 도메인을 등록하면 기존 github.io 주소가 자동으로 새 도메인으로 리다이렉트되는데, 이게 인증서 발급 전이면 접속이 불안정하게 보일 수 있습니다.

### 3-3. Geolocation(위치 정보) API는 HTTPS 필수
HTTP 상태에서는 브라우저가 위치 권한 팝업조차 안 띄우고 조용히 실패합니다. "특정 인앱브라우저에서 위치 기능이 안 된다"는 증상이 있을 때, 실제 원인이 브라우저 문제가 아니라 그 순간 HTTP로 접속되고 있었기 때문일 수 있습니다(실제로 이번에 이 원인으로 처음에 잘못 진단했던 사례가 있음 — 커스텀 도메인 인증서 미적용으로 HTTP 접속되고 있었음).

### 3-4. 네이버 인앱브라우저는 위치 기능이 원천적으로 제한될 수 있음
캐시·데이터 삭제로도 해결되지 않는 경우가 실제로 확인되었습니다(HTTPS 적용 후에는 문제가 해결된 것으로 보아, 결국 원인은 3-3과 동일했던 것으로 보이나, 인앱브라우저 자체의 제약 가능성도 완전히 배제되지는 않음). 코드로 해결 시도하기보다 "다른 브라우저로 열기" 안내가 실용적인 우회책입니다.

### 3-5. Claude Code의 60초 무응답 자동 진행 (AFK 모드)
Claude Code가 확인 질문을 던진 뒤 60초 동안 응답이 없으면, "최선의 판단으로 진행하라"는 내용이 자동 주입되어 스스로 판단해 진행하는 동작이 있습니다(공식 문서화 안 됨, 커뮤니티에서 발견된 이슈). 실제로 이 프로젝트에서 두 번 발생했습니다 — 한 번은 엑셀 컨택이력 컬럼 처리 방식을 임의로 선택(이후 되돌림), 한 번은 라이브 데이터의 빈 레코드(FAKE) 처리를 보류. 이후 "무응답 시에는 되돌리기 쉬운 보수적 선택을 하고, 반드시 다음 보고에 그 사실을 명시할 것"이라는 원칙을 세워서 적용 중입니다. 기술적 차단 방법으로 환경변수 `CLAUDE_AFK_TIMEOUT_MS`를 큰 값으로 설정하면 억제할 수 있습니다(비공식적으로 확인된 방법).

### 3-6. 로컬 프로젝트 폴더가 실제 배포본과 다를 수 있음
이 프로젝트는 원래 "코드 수정 → 파일 다운로드 → GitHub 웹사이트에 직접 업로드" 방식으로 작업해왔기 때문에, 로컬 D드라이브 프로젝트 폴더의 파일이 실제로 배포된 최신 버전과 다를 수 있습니다(로컬에 결과물을 다시 복사해 넣은 적이 없었기 때문). 실제로 GitHub 연동 작업 중 아이콘 파일 두 개가 로컬과 원격에서 서로 다른 버전으로 확인되어, 실제 배포된(GitHub) 버전이 맞는 최신본임을 사용자가 직접 스크린샷으로 재확인한 뒤에야 정리되었습니다.

### 3-7. 기존 GitHub 저장소와 로컬 폴더 연결 시 유의점
이미 커밋 이력이 있는 기존 저장소에 처음으로 git을 연결하는 경우, `git init` 이후 바로 `pull`하면 서로 무관한 히스토리로 충돌이 날 수 있습니다. 또한 git은 추적되지 않은(untracked) 파일을 병합 과정에서 조용히 덮어쓰는 것을 기본적으로 거부하므로, 실제로는 매칭되는 파일을 스테이징해 커밋한 뒤 병합하는 우회 방식이 필요했습니다.

### 3-8. clasp(Apps Script CLI) 설정 시 사람이 직접 해야 하는 단계
`clasp login`은 브라우저 OAuth 로그인이 필요해 자동화가 불가능하며, `clasp push`를 하려면 `script.google.com/home/usersettings`에서 "Google Apps Script API" 토글을 계정 소유자가 직접 켜야 합니다. 또한 `clasp push`로 코드를 올려도 실제 라이브 웹앱 URL에는 바로 반영되지 않으며, 별도로 `clasp deploy -i <배포ID>`를 실행해야 배포됩니다.

### 3-9. Google Apps Script 백엔드의 실제 저장 구조
겉보기와 달리 구글시트를 행/열 단위 데이터베이스로 쓰는 게 아니라, "데이터" 시트의 셀 A1 하나에 전체 데이터를 JSON 문자열 통째로 저장하는 구조입니다. 이 사실은 index.html(클라이언트 코드)만 봐서는 알 수 없고, Apps Script 서버 코드를 직접 열어봐야 확인 가능합니다. 원래 이 백엔드에는 동시 실행 잠금(LockService)이 전혀 없었으며, 이번에 새로 추가한 부분 업데이트 기능에만 적용했습니다 — 앞으로 서버 쪽에 쓰기 기능을 추가할 때마다 같은 잠금을 반드시 공유해야 합니다.

### 3-10. 저장 속도 문제의 실제 원인과 개선 한계
컨택 기록 하나만 추가해도 매번 전체 데이터(수십 KB)를 통째로 내려받고 다시 올리는 구조였던 것이 지연의 주 원인이었습니다(실측 3.6~5.0초). 부분 업데이트 기능 추가로 평균 2.1초까지 줄었으나, 남은 지연은 코드로 더 줄일 수 없는 Apps Script 자체의 요청당 실행 환경 준비 오버헤드로 확인되었습니다(실측 기반 결론). 추가 개선 여지로 "서버 응답을 기다리지 않고 화면을 먼저 갱신"하는 방식이 제안되었으나 미구현 상태이며, 구현 시 실패 알림 장치가 반드시 같이 있어야 데이터 유실을 막을 수 있습니다.

### 3-11. 열 자동 맞춤(auto-fit) 폭 계산과 컬럼 생성 로직은 분리해야 함
데이터가 없는 컬럼의 헤더 자체가 사라지는 버그가 있었는데, 이는 "폭을 계산하는 로직"과 "어떤 컬럼을 만들지 정하는 로직"이 얽혀 있어서 생긴 것으로 추정됩니다(코드·바이트 레벨 조사로도 재현은 안 됐으나, 실제 렌더링에서는 발생이 확인됨 — 자동화된 검증만으로는 못 잡아낼 수 있으니 실제 파일을 열어 눈으로 확인하는 절차가 필요). 이후 두 로직을 분리하고 최소 폭 방어 코드를 추가해 대응했습니다.

### 3-12. 코웨이 지도앱(coway-map)과 견적 자동화(coway-quote)는 별개의 GitHub 저장소
하나의 저장소 안에 폴더로 나뉜 게 아니라 처음부터 독립된 두 저장소입니다.
